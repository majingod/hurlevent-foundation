## 3. PersonnageNouveauV2.tsx

**Chemin :** `src/pages/PersonnageNouveauV2.tsx` (288 lignes)
**Dernier commit :** 2026-05-07 15:41:25 -0400

### Ce que fait ce fichier

Orchestre le wizard en 11 étapes. Responsabilités :

1. **Démarrage :** appelle `demarrer_creation_personnage()` (RPC sans paramètre) au montage. La RPC crée un brouillon si aucun n'existe, ou renvoie l'existant (`code: "brouillon_existant"`). Stocke `personnageId` et `etape_creation` en state local.

2. **État serveur :** query react-query `["v2-personnage", personnageId]` qui lit `personnages(id, nom, etape_creation, xp_total, xp_depense)`. Rafraîchi après chaque soumission d'étape via `queryClient.fetchQuery`.

3. **Progression :** `handleEtapeSuccess` recharge le personnage depuis la DB et avance sur `etape_creation` retourné par le serveur (le serveur est source de vérité). `handlePrevious` décrémente `etape` localement sans appel DB.

4. **Rendu :** switch conditionnel `{etape === N && <EtapeN_V2 ... />}`. Affichage barre XP disponible/dépensé/total en en-tête.

### Interface de props exportée

```typescript
export interface EtapeProps {
  personnageId: string;
  onSuccess: () => void;
  onPrevious?: () => void;
}
```

### Composants importés

Tous les 11 depuis `@/components/createur/etapes/` :

```
Etape1_V2, Etape2_V2, Etape3_V2, Etape4_V2,
Etape5_Competences_V2, Etape6_Sorts_V2, Etape7_Prieres_V2,
Etape8_Artisanat_V2, Etape9_Assemblages_V2,
Etape10_Historique_V2, Etape11_Recapitulatif_V2
```

### Gestion de l'étape courante

- **State local :** `const [etape, setEtape] = useState<number>(1)`
- **Source de vérité :** `etape_creation` dans la table `personnages` (lue via react-query après chaque soumission)
- **Pas d'URL parameter :** l'étape n'est pas reflétée dans l'URL (un rechargement de page repart de l'étape retournée par le serveur via `demarrer_creation_personnage`)

## 4. Routing

### Fichier de routing

`src/App.tsx` (164 lignes) — utilise React Router v6 : `BrowserRouter`, `Routes`, `Route`.

### Routes liées à `/personnage/*`

```tsx
// App.tsx lignes 51-74

<Route
  path="/personnage/nouveau"
  element={<ProtectedRoute><PersonnageNouveau /></ProtectedRoute>}
/>
<Route
  path="/personnage/nouveau-v2"
  element={<ProtectedRoute><PersonnageNouveauV2 /></ProtectedRoute>}
/>
<Route
  path="/personnage/:id"
  element={<ProtectedRoute><PersonnageFiche /></ProtectedRoute>}
/>
```

### `/personnage/nouveau-v2` — état actuel

**La route est câblée et fonctionnelle.** Elle a été ajoutée dans le commit `635418d`
(2026-05-07 01:00:00 +0000), en même temps que `PersonnageNouveauV2.tsx` et les étapes 1–4.

En React Router v6, un segment statique (`nouveau-v2`) a un score de correspondance
supérieur à un segment dynamique (`:id`), donc le routeur ne confond pas les deux routes
même si l'ordre de déclaration dans le JSX ne le garantissait pas.

### Route fallback `:id` potentiellement problématique

`/personnage/:id` (ligne 67-74) correspond à **tout** slug sous `/personnage/`. Si
`PersonnageNouveauV2` retournait une erreur de démarrage et que l'utilisateur naviguait
manuellement, la chaîne `"nouveau-v2"` serait traitée comme un UUID par `PersonnageFiche`,
déclenchant "Personnage non trouvé". Ce n'est plus le cas en navigation normale.

### Catch-all global

```tsx
<Route path="*" element={<Navigate to="/" replace />} />
```

Redirige tout chemin inconnu vers `/`.

## 5. State management du créateur

### V1 — `PersonnageNouveau.tsx`

**Pattern : props drilling massif via `useState` au niveau parent.**

Le composant parent déclare environ 20 états :

```
nom, gnCompletes, miniGnCompletes, ouverturesTerrain,
estCroyant, religionId, raceId, raceNom, raceNomLatin,
sousTypeChimeride, etape3PeutPasser, classeId, classeNom,
familleCriminelleId, familleCriminelleNom, psMax, pvMax,
competencesGratuites, xpDepart, xpDepense,
historique, amePersonnage
```

Ces états sont passés en props à chaque étape. La sauvegarde DB est centralisée
dans `sauvegarderEtape(nouvelleEtape)` qui effectue un `insert` ou `update` direct
sur la table `personnages`. Les composants d'étape V1 **n'appellent pas de RPC**
et ne font pas de requête DB directement.

Exception : `creer_demande_race` est appelée via une dialog modale dans `PersonnageNouveau.tsx`.

**Aucun Context React, aucun Zustand, aucune bibliothèque de state management globale.**

### V2 — `PersonnageNouveauV2.tsx`

**Pattern : état serveur via react-query + DB Supabase, état local minimal.**

Le parent ne maintient que :
```
personnageId (string | null)
etape (number)
demarrage (boolean)
erreurDemarrage (string | null)
```

Chaque composant d'étape lit et écrit directement la DB via un RPC dédié. Le parent
relit `etape_creation` depuis la DB après chaque soumission pour avancer. Les états
métier (nom, race, classe, XP…) ne transitent **jamais** par le parent — ils vivent
uniquement en DB.

L'affichage XP (total/dépensé/disponible) est calculé depuis la query react-query
sur le personnage, pas depuis des états locaux.

**Aucun Context React, aucun Zustand.** Pas de dossier `src/stores/`. Un seul fichier
dans `src/contexts/` : `AuthContext.tsx` (authentification uniquement).

### Pourquoi V1 est un mauvais patron direct

Les composants V1 (`Etape_*` dans `creation/`) n'appellent **aucune RPC** et n'écrivent
pas en DB. Ils remontent l'état au parent via des callbacks de type `setRaceId`, `setClasseId`,
etc. Ce paradigme est incompatible avec le design V2 où chaque étape est autonome et persiste
elle-même.

### Les `creation/*_V2.tsx` sont le bon patron

Les fichiers `Etape5–11_*_V2.tsx` dans `creation/` sont de vraies implémentations V2 :
- Utilisent react-query et les RPCs post-Migration 2
- Gèrent leur propre état local (sélection d'items, textes libres)
- Ont des comportements complets (achat/annulation item par item pour les étapes 5–9)

**Le seul travail requis** pour les intégrer dans `PersonnageNouveauV2.tsx` :

#### Incompatibilités de signature

| Composant (`creation/`) | Signature actuelle | Signature cible (`EtapeProps`) |
|---|---|---|
| `Etape5Props` | `onSuccess?(data: Json) => void; onError?` | `onSuccess: () => void` |
| `Etape6–9Props` | identique à Etape5 | identique |
| `Etape10Props` | `onSuccess?(data: Json) => void; onError?` | `onSuccess: () => void` |
| `Etape11Props` | `onComplete: () => void` | `onSuccess: () => void` |

#### Travail spécifique par étape

- **Étapes 5–9 :** ajouter un bouton "Suivant" (actuellement absent) qui appelle `onSuccess()`
  une fois les achats terminés. La RPC `acheter_*` est déjà invoquée item par item — aucun
  changement côté backend requis.

- **Étape 10 :** renommer `onSuccess?` → `onSuccess` (non optionnel), supprimer `onError`.

- **Étape 11 :** renommer `onComplete` → `onSuccess`.

### Verdict

**Le V1 pur n'est pas un bon patron pour reconstruire le V2.** Il peut servir de référence
UI/UX (quelles informations présenter) mais son architecture de state est incompatible avec
le design V2.

**Les `creation/*_V2.tsx` (mis à jour dans PR #35) sont le bon patron.** Ils représentent
entre 1 et 3 heures de travail d'adaptation par étape (signature + bouton "Suivant"),
non un refactoring complet.

## 7. Découverte importante — Double dossier V2

L'audit révèle une source de confusion architecturale majeure : **deux dossiers contiennent
des fichiers `Etape*_V2.tsx`** qui ne communiquent pas.

```
src/components/creation/          ← dossier V1 + implémentations intermédiaires V2
  Etape_InfosBase.tsx             ← V1 (sans _V2)
  Etape5_Competences_V2.tsx       ← implémentation V2 réelle, NON importée par le wizard
  Etape6_Sorts_V2.tsx             ← idem, mise à jour PR #35
  ...

src/components/createur/etapes/   ← NEW dossier — composants du wizard actif
  Etape1_V2.tsx                   ← fonctionnel
  Etape5_Competences_V2.tsx       ← STUB — même nom, chemin différent
  ...
```

`PersonnageNouveauV2.tsx` importe depuis `@/components/createur/etapes/` (stubs),
**pas** depuis `@/components/creation/` (implémentations réelles). La migration
consiste à adapter les `creation/*_V2` et les déplacer/réécrire dans `createur/etapes/`.
